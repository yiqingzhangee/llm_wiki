## 你设计线上 / 离线双 Runtime 架构的业务痛点是什么？两套架构分别做了哪些差异化设计？

拆分双 Runtime 核心是两类任务的诉求完全不同：线上单点分析对接人工审核、应急排查，要求低延迟、高并发；离线批量任务面向全量巡检、复盘分析，任务耗时久、容易出现进程中断、状态丢失，同时批量调用 LLM 需要严格控制成本。

基于痛点做差异化设计： 线上 Runtime 基于 pydantic\-ai \+ Orchestrator\-Worker 架构，采用 Sequential 短路流水线，高优风险命中后直接终止流程；同时搭配 Strictest\-Win 并行多 Policy 子 Agent，从严判定保障风险不漏，全程优先压缩响应耗时。 离线 Runtime 基于自研 Durable Queue 持久队列，搭配 Lease 租约 \+ Heartbeat 心跳机制，节点异常可自动重发任务，彻底解决长任务状态丢失问题；结合 Skill\-based SOP 标准化流程、Quick Mode 后台执行，结果通过飞书卡片统一回推。整套架构解耦了 LLM 与工具调用，既实现风控规则分钟级更新，也将整体 Token 成本优化 40%。

## 详细讲解 pydantic\-ai \+ Orchestrator 的整体架构设计与执行逻辑

整套架构分为四层：接入层、自研 Orchestrator 编排层、pydantic\-ai Agent 层、底层工具能力层。 接入层负责接收视频数据、做预处理和参数校验；Orchestrator 是调度中枢，负责定义执行拓扑、流程流转、任务分发与结果聚合，支持两种核心执行模式。 第一种是串行短路流水线，按风险优先级依次执行 Agent，命中风险立即停止后续流程，实现快速放行 / 拦截；第二种是并行多 Policy 子 Agent，多个风控维度 Agent 同时运行，采用 Strictest\-Win 从严判定，任意 Agent 识别违规即判定为风险。 pydantic\-ai 作为 Agent 底座，依托原生强类型校验、Function Call 工具调用、上下文管理能力，封装画面、文本、闪帧等多个独立风控子 Agent。底层对接抽帧、OCR、图片黑库、分类模型等风控工具。 架构采用分布式 Worker 节点部署，增加超时熔断机制保障线上稳定性；同时将风控规则、提示词配置化，无需改代码即可更新标准，LLM 调用统一管控，兼顾迭代效率与成本控制。

## 在色情闪帧专项治理中，你针对抽帧策略和模型检测分别做了哪些针对性优化？

闪帧画面停留时间极短、常规采样容易漏检，我从抽帧和模型两方面做专项优化。 抽帧策略上，采用粗筛 \+ 精检分层模式：粗筛用低频抽帧过滤大部分正常视频；疑似风险视频启动毫秒级密集抽帧。同时做动态密度调控，对高风险账号、画面亮度 / 像素突变的时域区间，自动提升抽帧密度；搭配滑动窗口采样，避免帧间隔卡在违规画面间隙导致漏检。

模型检测方面：第一，采用多帧特征融合，结合帧间时序特征区分正常镜头转场和恶意闪帧；第二，基于 Dinvo2 小样本模型，搭配闪帧专属数据增强、线上难例挖掘，快速适配不断迭代的违规变种；第三，搭建多模型串联校验链路，轻量化模型初筛、精细模型精判、图片黑库交叉比对，在提升召回的同时控制误判；最后对临界置信度样本做二次复检，进一步优化效果。

## 短视频场景下，相似帧去重你使用了哪些方案，不同方法的适用场景是什么？

我们采用多级联动的去重方案，不同算法各司其职：

1. aHash/dHash：速度最快，主要用于单视频内部冗余帧过滤，清理高密度抽帧产生的重复画面，减少下游推理压力；缺点是对调色、翻转抗性弱。

2. pHash：基于 DCT 变换，抗缩放、裁剪、转码、轻度滤镜能力强，是核心主力，用于违规图片黑库匹配、跨视频同源闪帧 / 搬运内容溯源。

3. ORB 特征点：针对黑产画面翻转、局部遮挡、异形裁剪等对抗篡改场景，作为精判手段使用，计算耗时更高，不做全量遍历。

4. 深度语义 Embedding：应对重度二创、换背景等像素差异大但语义一致的内容，结合向量数据库做大规模检索，适合复杂对抗场景。

线上主流以哈希方案为主，粗筛 \+ 精判组合，平衡性能、成本与识别精度。

## 请详细讲解基于 DCT 离散余弦变换的 pHash 感知哈希原理

pHash 全称感知哈希，依靠 DCT 离散余弦变换提取图像主体特征，整体分为六步：

1. 图像预处理：将任意尺寸图片统一缩放到 32×32，并转为灰度图，消除分辨率、色彩干扰；

2. DCT 变换：把像素空间域矩阵转为频率域矩阵，图像主体轮廓集中在低频区域，噪点、细节、滤镜属于高频区域；

3. 截取低频区域：只保留 DCT 矩阵左上角 8×8 的低频系数，舍弃全部高频信息；

4. 计算均值：求出 8×8 共 64 个系数的平均值，作为二值化阈值；

5. 生成哈希指纹：系数大于均值记为 1，小于均值记为 0，拼接得到 64 位二进制哈希串；

6. 相似度判定：计算两张图片哈希串的汉明距离，距离越小代表画面越相似。

因为过滤了高频干扰，pHash 对缩放、裁剪、压缩、轻度调色都具备很强鲁棒性。

## 完整介绍风控场景下样本回流的全流程，以及针对新型未知违规的加急处理方案

样本回流分为实时应急回流和离线批量回流两条链路，整体流程共 6 个环节：

1. 数据采集：统一接入四大数据源 —— 模型漏判样本、模型误判样本、用户举报 / 运营巡检样本、专项定向抓取样本，通过消息队列统一收口；

2. 分层降噪：利用帧哈希去重剔除重复内容，基于模型置信度筛选临界样本，同时做风险类型预分类，过滤大量无效数据；

3. 数据标准化：对视频抽帧、提取 OCR / 音频文本，挂载账号、设备、行为等多维特征，统一数据格式；

4. 分池分发：按照紧急程度、风险类型、难度划分样本池（应急池、常规漏判池、误判池、疑难池），自动分发至标注平台；

5. 多级标注质检：执行标准化标注规则，采用一审 \+ 二审复核机制，确保标注质量；

6. 样本入库：标注完成后分区存入样本库，分别供给模型训练、规则更新、基线评测、案例复盘使用。

针对新型未知 0day 违规，开启应急通道：跳过部分常规过滤逻辑，优先分配标注人力；依靠小样本模型实现几十条样本即可增量迭代，同时同步更新规则库、黑库，从发现风险到模型 / 策略上线最快数小时完成。

# 第二部分：高频延伸追问 \+ 完整回答

## 为什么选择 pydantic\-ai，而不用 LangChain 等其他 Agent 框架？

主要基于线上风控低延迟、高并发、稳定性三大要求选型： 第一，我们的 Agent 以短流程、少轮次工具调用为主，pydantic\-ai 足够轻量化，启动开销和推理延迟远低于 LangChain； 第二，它原生基于 Pydantic 做强类型校验，能严格约束 LLM 输入输出格式，避免格式异常导致线上服务报错，稳定性更强； 第三，二次封装简单，团队上手快，适合风控策略高频迭代的场景。LangChain 组件冗余、体量较重，更适合复杂长对话场景，不适合我们高并发线上链路。

## Strictest\-Win 并行多 Policy 子 Agent 的落地逻辑是什么，结论冲突如何处理？

我们将不同风控维度拆分为独立子 Agent 并行执行，Strictest\-Win 就是从严判定逻辑：只要任意一个子 Agent 判定内容违规，最终结果就判定为风险；只有所有 Agent 全部判定正常，才予以放行。 这套逻辑贴合内容风控 “严防风险外泄” 的底线要求。多个 Agent 结论冲突是常态，我们不做投票折中，始终以 “检出风险” 为优先，从源头降低漏判率。

## Durable Queue \+ Lease/Heartbeat 心跳机制的实现逻辑是什么？

Durable Queue 是持久化队列，会完整记录每一条任务的进度、状态与归属。 任务节点从队列领取任务后，会持有对应租约，并持续向服务端上报心跳；如果节点宕机、进程卡死，心跳会中断，租约自动过期。此时系统判定任务执行异常，自动将任务放回队列，由其他空闲节点重新领取执行。整套机制保证大批量长任务不会丢失、不会卡死。

## 闪帧场景下，多帧融合是采用 3D 卷积还是特征拼接？为什么这么选择？

线上实时链路优先使用相邻帧特征拼接 \+ 2D 卷积的轻量方案，推理速度快、算力开销小，满足低延迟要求；仅在离线精检、离线样本分析场景，使用简易 3D 卷积提取完整时序特征，提升精度。 整体以轻量方案为主，兼顾线上性能与基础识别效果。

## 高密度抽帧会带来算力压力，你做了哪些成本与性能优化？

主要做四类优化：

1. 动态抽帧：仅对高风险视频、画面突变片段做密集采样，普通视频保持低频抽帧；

2. 图像预处理：统一压缩分辨率，在不影响特征的前提下减少计算量；

3. 推理优化：模型量化、批次合并、异步流水线执行，提升单机吞吐；

4. 数据清理：临时抽帧图片不做持久化存储，分析完成立即清理，降低存储与 IO 压力。

## 如何区分恶意色情闪帧和短视频正常特效、镜头转场？

从内容特征 \+ 时序特征双维度区分： 正常转场、灯光特效具备语义连续性，帧间变化有规律；恶意闪帧不仅画面内容违规，帧间变化突兀、无逻辑。同时联动图片黑库、OCR、语义模型做多维度交叉校验，综合结果判定，有效降低误判。

## pHash、ORB、SIFT 如何选型？pHash 的相似度阈值如何设定，踩过哪些坑？

选型规则：常规相似帧匹配、黑库检索用 pHash；画面翻转、遮挡等对抗场景用 ORB；SIFT 因专利问题、速度慢，商用线上基本不使用。 pHash 以汉明距离为阈值：行业通用≤5 判定为高度相似，6\~10 进入精判，＞10 判定不相似。 踩过的主要坑：全屏纯色、全黑 / 全白等低熵画面极易出现哈希碰撞，我们前置图像熵值过滤，提前剔除这类无效帧，避免大量误判。

## 海量帧数据做哈希比对，如何优化计算效率？

1. 采用滑动窗口局部比对，只和窗口内历史帧对比，把时间复杂度从 O \(n²\) 降到 O \(n\)；

2. 哈希值转为 uint64 整数存储与比对，比字符串效率更高；

3. 哈希分桶，检索时只查询对应分桶，不用全库遍历；

4. 连续多帧相似时启用 early\-stop，跳过后续无效计算。

## 内容风控中，团伙挖掘场景下图规模容易膨胀，你做了哪些性能优化？

1. 前置账号初筛，低风险账号不纳入图计算，从源头缩小图规模；

2. 对关联边做权重打分，只保留高置信度强关联边，过滤噪声弱边；

3. 采用分布式图分片计算，横向扩容集群；

4. 缩小单次社区搜索半径，采用局部多轮搜索替代全局遍历，控制计算量。

## 长短周期团伙模型，在短视频养号场景中是如何划分周期、识别不同团伙的？

短周期团伙：注册后数天内集中发布违规内容、批量互动，生命周期短，属于临时突击作弊； 长周期团伙：持续数周甚至数月模拟正常用户行为养号，逐步提升账号权重，后期再发布违规内容。 模型依靠活跃周期、行为曲线、内容发布节奏自动区分两类团伙，针对性挖掘与防控。

## 团伙挖掘能力如何和 LSTM 时序模型、内容检测模型做联动？

分为双向联动：

1. 前置召回：将挖掘出的团伙账号名单，送入行为时序模型、内容检测模型，做定向加强检测，提升风险召回；

2. 后置溯源：模型识别出的风险账号，反向送入图挖掘模块，查找其关联团伙，实现 “发现一个、挖出一群” 的集群式打击。
