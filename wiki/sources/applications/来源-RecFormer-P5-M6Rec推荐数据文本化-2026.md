## 核心结论

“推荐数据文本化”至少有三种不同的统一对象，不能混称为“生成式推荐”：

| 路线 | 统一对象 | 主要输出 | 工程边界 |
|---|---|---|---|
| RecFormer | 物品属性与历史的输入表示 | 历史/物品向量与相似度检索 | 文本编码不等于生成物品 |
| P5 | 任务接口与 input→target 格式 | token 序列 | 固定标签/大候选池未必经济 |
| M6-Rec | 共享骨干 | 分类头或自回归生成 | 输出头仍应服从任务约束 |

## 三种机制

- **RecFormer**：将键值属性展开为物品句子，用 token 类型、token 位置和物品位置重新标记被展平的字段角色与历史边界；用户历史和候选物品分别编码后，以向量相似度进行下一物品检索。
- **P5**：把评分、顺序推荐、解释、摘要等任务改写为 prompt 与目标文本，使用统一 encoder–decoder 和 token 级损失。它证明语言接口可统一任务格式，但不证明所有任务都应使用生成式输出。
- **M6-Rec**：在同一骨干中保留双出口。CTR/CVR 等闭集任务取隐藏状态接分类头；解释、搜索词或对话等开放任务再使用自回归生成。

## 对分类与风险任务的启示

可复用的起点是：**RecFormer 式确定性字段/历史序列化 + P5 式任务说明 + M6-Rec 式判别头**。它保留了字段名、时间顺序和任务语义，同时对固定类别直接输出 logits，便于校准、低时延服务与规则消费。

这只是架构组合假设，不是跨域效果结论。若字段只是匿名 ID、数值精度或缺失模式构成关键信号，必须与连续特征分支、GBDT/GRU 及晚融合路线公平比较。

## 不确定性

- 三篇研究的任务、候选规模、模型主干和训练协议不同，不能用单一离线分数横向排名。
- 物品 ID 或评分 token 能被生成，并不代表生成比分类、向量检索或目录受限打分更低成本或更可靠。
- 文本化会压缩结构；字段角色、物品边界、顺序、数值精度和可见时点需要由模板、embedding 或专用分支显式恢复。
