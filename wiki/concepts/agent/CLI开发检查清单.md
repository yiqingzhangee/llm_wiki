# CLI 开发检查清单

> 依据：[[多平台CLI的分层封装与草稿发布生命周期]]。适用于把平台接口封装成 CLI 命令，或为已有 CLI 增加能力。
>
> 本清单是开发建议，不是某个具体产品的强制规范。平台名称、接口、认证和发布命令须按实际项目填写；内部证据保留在受控位置，公开文档只记录脱敏结论。

## 使用方法

按阶段执行。复选框表示已经验收，不表示“已经开始”或“代码已经写完”。每个阶段填写产物或验证证据；不适用项记录理由，不直接略过。接口契约、资源标识或写入语义不明确时，先解决该项再继续开发。

这是一份可复用模板。为一个实际功能执行时，复制清单到该项目，填写任务信息和证据位置。

## 任务信息

| 字段 | 填写内容 |
|---|---|
| 用户任务 | 一句话说明用户要完成什么 |
| 命令形式 | 命令路径、参数和一个典型调用 |
| 项目与实现位置 | 仓库、模块、分支 |
| 支持范围 | 区域、环境、资源类型 |
| 操作性质 | 只读、修改草稿、提交版本、发布或其他 |
| 默认副作用 | 不传任何可选开关时会发生什么 |
| 完成判据 | 用户能观察到的最终结果 |
| 证据位置 | 契约、样例、测试和集成验收记录 |

## 阶段一：确认用户任务与接口契约

**操作**：先查平台文档；必要时查看控制台真实操作的请求。将一次用户操作涉及的全部请求列出来。

- [ ] 写出正常流程、输入不合法时的行为和平台拒绝时的行为。
- [ ] 记录每个接口的方法、路径、必需字段、响应和业务错误。
- [ ] 区分用户输入、页面临时字段、服务端生成字段；标注哪些判断尚未验证。
- [ ] 确认接口需要完整草稿还是局部补丁，以及省略字段与显式传空值的区别。
- [ ] 确认资源 ID 的类型、来源和关联方式；区分编辑节点、调度任务、版本和执行记录。
- [ ] 记录区域路由与认证方式；只保留脱敏请求样例。
- [ ] 确认接口是同步完成还是异步受理；找到后续状态查询方式。

**产物**：接口契约表、脱敏请求与响应样例、资源标识关系、待验证问题。

**通过标准**：开发者能够说明“向哪个环境的哪个对象发送什么请求，以及如何判定结果”。源码、帮助和技能说明来自同一项目时，不将其算作独立服务端验证。

## 阶段二：定义命令与结果契约

**操作**：围绕用户任务设计命令，列出参数、默认值和结构化结果。

- [ ] 单一接口语义清楚时直接封装；多个接口完成一个任务时定义业务编排。
- [ ] 一个接口承载多个动作时，分别定义命令或明确的模式参数。
- [ ] 对每个参数注明类型、必填条件、默认值、范围及互斥关系。
- [ ] 明确追加与替换、保存与提交、提交与发布的区别。
- [ ] 写命令明确预览与实际写入的入口；兼容已有命令时记录其现有默认行为。
- [ ] 预览展示目标资源、环境和预期变更；明确预览不会调用业务写接口。
- [ ] 定义结果状态，区分请求受理、等待检查或审批、操作完成、失败和结果未知。
- [ ] 定义退出码；待处理状态是否返回零须与命令说明一致，不能用零退出码声称发布完成。
- [ ] 定义 JSON 输出字段和空值含义；在 JSON 模式下将进度、日志与诊断放到 stderr。
- [ ] 异步操作保留事件、版本或执行标识，提供后续查询方法。

**产物**：参数表、默认行为表、文本与 JSON 输出样例、错误与退出码约定。

**通过标准**：只看帮助和输出，用户就能判断是否发生写入、当前处于什么状态、下一步如何核验。

## 阶段三：按分层实现

**操作**：先复用项目已有认证、HTTP、错误和输出设施，再补功能代码。

- [ ] 命令层只承担注册、参数解析和帮助说明。
- [ ] Handler 校验输入、调用业务函数并组织输出。
- [ ] 多接口编排、资源 ID 转换、字段合并和去重放在 Service。
- [ ] API 层构造请求、解析响应、转换类型并归一平台错误。
- [ ] 区域和认证差异集中在适配层；未知环境明确报错，不自动换环境尝试写入。
- [ ] 认证失败、权限不足和业务失败有可区分的错误；日志不输出令牌、Cookie 或完整敏感载荷。
- [ ] 设置项目适用的请求超时；只对语义明确且可以安全重复的请求使用自动重试。
- [ ] 请求超时或连接中断后，若不能确认写入结果，报告“结果未知”并提供查询入口。

**产物**：分层实现、共享设施复用说明、错误处理和重试策略。

**通过标准**：业务编排可以脱离终端输出测试，HTTP 和认证可以替换为测试桩。

## 阶段四：选择专项检查

### A. 依赖或配置增量修改

- [ ] 读取最新草稿；字段解析失败时停止，不将损坏数据静默当成空配置。
- [ ] 明确去重键；依赖去重至少考虑上游资源、周期偏移和偏移类型。
- [ ] 保留现有依赖及无关配置；需要全量保存时确认序列化不会丢字段。
- [ ] 空增量或全部重复时返回无变化，不执行不必要的保存。
- [ ] 预览和写入使用同一套变更计算逻辑。
- [ ] 服务端支持版本条件写入时使用它；否则写前再次读取并比较，明确仍有竞态窗口。
- [ ] 草稿发生并发变化时停止写入，不自动拿旧值覆盖。
- [ ] 写后回读，核验新增内容、原有内容和无关字段。
- [ ] 忽略服务端管理字段时使用明确名单，并说明理由。
- [ ] 写入成功但回读校验失败时返回“已写入、核验失败”，不得自动盲目重试。

**通过标准**：新增目标内容，原有内容与无关配置保留；重复调用不新增重复项。客户端回读不作为原子更新保证。

### B. 代码或 Notebook 草稿保存

- [ ] 确认内容格式和编码；区分源代码文本、Notebook 对象与序列化字符串。
- [ ] 确认 metadata 必填条件；修改局部配置时读取并合并已有元数据。
- [ ] 区分编辑节点和调度任务标识，验证转换结果属于目标资源。
- [ ] 内容可能独立存储时实现对应读取路径；不能把正文缺失默认解释为空文件。
- [ ] 明确保存是否仅更新草稿，以及是否附带其他副作用。
- [ ] 保存后按平台能力回读内容或版本；允许平台规范化时定义等价判据。

**通过标准**：内容正确、元数据未意外丢失，输出准确说明草稿状态。

### C. 提交与发布

- [ ] 确认“提交”的平台含义，以及它与 Git 提交是否有关。
- [ ] 核对自动发布、流水线和审批的默认值，并写入帮助与测试。
- [ ] 只提交和提交后发布生成不同且可核验的请求。
- [ ] 从业务响应识别阻塞、待审批和失败，不仅检查 HTTP 状态码。
- [ ] 等待模式轮询明确的业务状态；超时输出当前状态与查询标识，不声称完成。
- [ ] 不等待时返回“已受理”及后续查询方式。
- [ ] 发布验收读取目标环境的生效版本或对应状态，不能只依赖提交接口成功。
- [ ] 已发布版本的恢复方式按平台能力说明；不得把重新保存草稿当作发布回滚。

**通过标准**：用户能够区分草稿保存、版本提交、发布受理和实际生效。

## 阶段五：离线验证

**操作**：按照功能行为选择用例，模拟平台响应与并发变化，不要求真实认证。

| 验证组 | 必须检查的行为 |
|---|---|
| 参数与默认值 | 缺必填项、非法类型、互斥参数、默认副作用 |
| 响应与输出 | 正常响应、空值、异常字段、业务错误、JSON 与 stderr 分离 |
| 认证与环境 | 路由正确、认证失败、无权限、未知环境 |
| 增量修改（适用时） | 去重、无变化、预览零写入、写前冲突、写后失败、无关字段保留 |
| 保存（适用时） | 内容格式、元数据合并、ID 关联、独立正文读取 |
| 提交发布（适用时） | 只提交、提交并发布、待检查、待审批、失败、超时结果未知 |

- [ ] 从表中选择适用用例，给每个用例写出可观察的断言。
- [ ] 在项目惯用的 API 或服务边界 mock，避免测试仅重复内部实现。
- [ ] 验证预览、冲突、非法参数等路径没有调用业务写接口。
- [ ] 验证失败后没有无条件重试非幂等写入。
- [ ] 运行项目实际提供的构建、类型检查、格式检查和测试命令。

在实现项目中填写下表后执行，不能把 Wiki 仓库当作目标 CLI 项目。不要默认项目存在某个 npm 脚本。

| 检查 | 实际命令 | 结果与证据 |
|---|---|---|
| 构建 | 待填写 | 待填写 |
| 类型检查 | 待填写；无静态类型时注明 | 待填写 |
| 格式与静态检查 | 待填写 | 待填写 |
| 功能测试 | 待填写 | 待填写 |
| 差异检查 | Git 项目可用 `git diff --check` | 待填写 |

**通过标准**：适用检查全部通过且保留实际输出。某项未执行，验收记录就明确写“未验证”。

## 阶段六：受控集成验收

**操作**：使用该项目明确授权的测试环境与资源执行真实接口验收。生产发布单独遵循该项目的授权流程。

- [ ] 先核对身份、环境和目标资源，再执行只读查询。
- [ ] 写操作保存变更前快照，先验证预览内容。
- [ ] 执行目标操作并记录请求标识、操作结果和时间。
- [ ] 回读目标资源；异步操作追踪到明确终态，或记录仍待处理。
- [ ] 核验实际变更及无关字段；发布检查目标环境的生效版本。
- [ ] 记录测试资源清理或恢复情况；涉及再次写入时确认仍在授权范围。
- [ ] 对未覆盖的区域、资源类型和平台行为标注验证边界。

**产物**：集成验收记录、脱敏前后差异、操作状态与证据。

**通过标准**：真实平台行为符合命令契约；未做集成验证时只报告离线验证通过。

## 阶段七：文档与发版验收

- [ ] 更新帮助：参数、默认值、副作用、输出状态与典型调用。
- [ ] 更新技能或自动化说明：资源 ID、预览、状态查询和结果未知时的处理。
- [ ] 有 MCP 等入口时确认命令可发现，参数和行为与 CLI 一致。
- [ ] 更新变更说明，记录兼容性变化和已验证范围。
- [ ] 按项目发布流程构建并发布；不假设所有项目都使用 npm。
- [ ] 从实际安装的制品检查版本、帮助和只读调用。
- [ ] 若发布后再做写入冒烟，使用已授权的测试资源并重新核对环境。
- [ ] 检查交付包与公开说明不含凭据、内部请求样例或敏感数据。

**通过标准**：安装制品与验证版本一致，用户说明与实际行为一致。

## 验收结论模板

```text
命令与版本：
实现范围：
默认副作用：
离线验证：通过 / 失败 / 未执行；证据：
集成验证：通过 / 失败 / 未执行；环境与证据：
写入结果：不适用 / 未写入 / 已写入 / 结果未知；证据：
发布状态：不适用 / 未受理 / 待处理 / 已生效 / 失败 / 未知；证据：
剩余限制与不适用项理由：
安装制品与文档：
结论：可交付 / 待验证 / 不通过
```
