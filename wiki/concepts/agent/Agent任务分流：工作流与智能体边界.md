# Agent任务分流：工作流与智能体边界

> 关联来源：[[来源-构建Agent的四个问题-2026-06-21]]

## 核心问题

在工程实践中，关键不是“能不能用 Agent”，而是“这个任务是否值得且适合用 Agent”。

## 四问分流框架

### 1) 复杂度

- **低复杂度**：优先 workflow（规则明确、步骤固定、状态可枚举）。
- **高复杂度**：再考虑 agent（需要动态规划、开放式决策、跨工具探索）。

### 2) 价值

- **低价值任务**：默认 workflow，避免过度自治带来的额外治理成本。
- **高价值任务**：可引入 agent，但前提是收益覆盖观测、审计、回滚等配套成本。

### 3) 可执行性

- 若任务链路中存在不可执行环节，应先做范围收缩与接口补齐，再进入 agent 化。
- “先上 agent 再补能力”通常会把问题从功能缺失转成稳定性与责任归因问题。

### 4) 错误成本

- **高错误成本**：默认只读、审批门或人类在环（HITL）。
- **低错误成本**：可放宽执行权限，优先追求自动化吞吐。

## 反模式提醒

1. **把 Agent 当默认方案**：忽略任务价值和风险，导致“技术上可行，业务上不划算”。
2. **把 workflow 与 agent 对立化**：正确方式通常是分层组合，而非二选一。
3. **无门禁直接放权**：在高错误成本场景中会放大越权、误操作与追责困难。

## 不确定性

- 四问框架当前来自经验归纳，缺少跨行业统一阈值；应按业务域、监管要求、SLA 目标本地化。
