## 一、决策模型与能力分层

### Jev：把有界判断从生成主循环拆出

《一文讲清 Jev》和《Jev 实测》形成了互补证据：

- Jev 接收 `State` 和预先声明的 `Questions`，返回 `Choice`、`Score`、`Noul` 及概率；
- 输出 Schema 有界，可以防止模型生成未声明的选项，但不能保证合法选项中的判断一定正确；
- 适合模型路由、工具风险门控、结果校验、检索过滤和大规模分类；
- 不适合开放式写作、代码生成、精确计算、未知值抽取和需要隐式多步推理的问题；
- 更合理的系统分工是“通用模型负责生成与复杂推理，Jev 负责高频小判断，代码负责执行”。

内部实测进一步补充了两个边界：

1. Jev 与 Seed 2.0 Lite 在多数语义分类、是非和评分任务上的判断方向相近；
2. 分歧集中在精确大数运算和业务规则未定义的日期判断，这类问题应由代码先计算或明确规则。

概率值也不能直接当作真实正确率。相同结论在不同措辞下可能出现概率波动，无意义输入有时仍会得到高置信答案。因此自动分流前需要在自有数据上校准阈值，并设置拒绝、升级和回退路径。详见 [[Jev决策模型与Agent架构]]。

### 模型能力需要按任务形状拆分

《写给 RD 的 AI 底层原理》提供了模型侧背景：Embedding、Attention、GQA、多模态、深度思考、端侧部署、Mamba、Function Call、采样与幻觉分别解决不同问题。榜单中的 GPT 6 Astra 文章则以 Computer Use 和界面理解为关键词。

这组内容说明，模型选型不应只按“谁最强”排序，而应先区分任务形状：

```text
开放生成与复杂推理 → 通用前沿模型
有界语义判断       → Jev 等决策模型
界面理解与操作     → Computer Use 模型
精确计算与硬规则   → 普通代码
```

## 二、Harness、编排与持续进化

### AutoResearch：从会写代码到会跑实验闭环

AutoResearch 的核心不是让 Coding Agent 多写几段代码，而是把算法研发组织成：

```text
定义任务与评价
→ 提出改进方案
→ 修改代码并执行实验
→ 判断结果
→ 选择下一步
→ 沉淀经验
```

其 RSI 实践进一步允许 Harness 在冻结任务、统一评分和版本晋级条件下修改自己的搜索策略、实验组织与经验使用方式。活动页报告：

- 递归迭代后框架综合得分相对提升 70.1%；
- 商品图片 Reward Model 的 GAUC 从 0.8611 提升到 0.8906；
- 新模型用于 DPO 生图策略后，生效范围取得 advv +2.71% 的线上收益。

这些数字是单项目内部口径，支持“受控任务内的 Harness 改进可产生业务收益”，但不能证明开放式、跨任务 RSI 已经成立。它与 [[递归自我改进与Harness自演化]] 的既有边界一致。

### Agent Team：把编排当作分布式系统

多 Agent 长文将长期 Agent 协作拆成一组明确语义：

| 对象 | 职责 |
|---|---|
| `Agent` | 长期身份、能力、关系和版本 |
| `Workspace` | 成员与协作权限 |
| `Channel` | 跨任务共享的项目背景 |
| `Thread/DM` | 收窄话题或受众 |
| `Task` | 目标、负责人、状态、验收条件 |
| `Run` | 一次真实执行及工具活动 |
| `Session` | 可恢复但会衰减的运行上下文 |
| `Computer` | Agent 的执行设备与本地环境 |

其关键设计不是“多开几个 Subagent”，而是处理分布式系统问题：

- **身份与会话分离**：Agent 长期存在，Session 在压缩收益过低或持续高压时换代；
- **有限共享上下文**：Channel 只传播结论、证据、求助和交接，工具尝试留在各自 Session；
- **Task/Handoff/Gate**：创建任务时定义要求和验收证据，交付后由人、代码或 Reviewer Agent 验收；
- **注意力调度**：权限决定能否读取，注意力策略决定是否唤醒；Inbox、租约和新鲜度检查防止重复执行与过时回复；
- **故障恢复**：根据超时、上下文耗尽、任务版本和负责人变化选择恢复原 Session、新建 Session 或停止恢复；
- **版本治理**：Agent Revision、变更提案、对照评测和 Team Lockfile 保证每次 Run 可追溯；
- **多层 Loop**：主 Task 记录外层选择循环，子 Task 承载具体改动和返工循环。

这与 [[Agent本体论]] 中的 `AgentInstance`、`Task`、`Action`、`Trace` 和 `Delegation` 形成直接工程映射。

### bytedcli：把组织能力变成 Agent 可依赖的接口

bytedcli 分享聚焦一行命令统一 Codebase、Bits、TCC、TCE、RDS 等平台，并讨论快速迭代、质量稳定和 Agent 生态。它代表 Harness 下方的工具层：Agent 不应为每个平台重新理解网页交互，而应通过稳定、可发现、可审计的 CLI/API 获得能力。

因此，CLI 的价值不只是“人少敲几条命令”，而是把组织平台能力转换为 Agent 能稳定调用的工具契约。

### 主动式数字分身：从请求响应转向持续感知

Jarvis 分享把主动式数字分身拆成三部分：

1. 持续更新的人、项目、事项、群和资源世界模型；
2. 快慢脑协作下的“感知—判断—执行—验证”闭环；
3. 审批、等待、人工确认和静默结束等主动性边界。

它与普通问答 Agent 的差异在于触发源：不再只等待用户的一句指令，而是把群聊、会议、文档和项目变化转换为线索和任务，再把执行结果沉淀回世界模型。风险也随之上升，因此审批与静默结束必须是一等状态，而不是提示词中的一句约束。

## 三、领域工作流、知识与经验闭环

### Argos × AgentBox：Oncall 经验连续性

Oncall 实践将大群值守、建群协作、知识检索、案例归档和周报连接起来：

```text
大群告警
→ Argos 前置分析
→ AgentBox 建群并触发 onboard/分析
→ 检索历史案例与 SOP
→ 人与 POC 推进处置
→ 人工触发案例记忆与周报
```

当前接入的 4,764 条告警卡片中，4,074 条至少收到一条 AI 回复，回复覆盖率为 85.5%；1,024 条 AI 回复出现历史案例或相似历史检索说明。这里的“回复覆盖”和“历史检索”不等于问题解决率，文章也明确保留人工判断、根因待确认和建议是否被采纳等边界。

它的关键价值是让一次处理同时服务当前协作和下一轮值班。当前事件收尾仍由人触发，群静默后的自动总结仍在建设。

### Aide 数据开发：知识网络、Skill 和编排三层

Aide 实践把数据需求开发组织为三层：

1. **知识网络**：融合业务语义、DSL 技术语义、三级分域规范、个人与任务记忆；
2. **专业 Skill**：覆盖需求澄清、模型设计、数据开发、测试和知识沉淀；
3. **开发编排**：Router 选择标准、直接或定制路径，编排协议连接上下游产物，上下文管道保留目标和关键决策。

其核心约束是“单点 Skill 保持专业自治，但不拥有全局决策权”。分域知识通过渐进披露进入当前阶段，确定性口径尽量由 DSL 和规则比较，而不是完全依赖模型推理。

2026-07-01 至 2026-08-21 的内部统计显示：端到端完成 115 个需求，用户渗透率 66%，平均提效 20.7%，正反馈率 78.7%；技术口径准确率 80.9%，技术方案准确率 68.6%。不同阶段覆盖率差异较大，数据测试只覆盖 43/115 个需求，因此这些指标不能理解为全流程已完全自动化。

### 知识工程：从文档维护转向指标闭环

知识工程实践将系统分成：

- **数据资产**：PRD、会议纪要、任务版本、初始代码、AI 产物、Trace、最终 MR 等客观事实；
- **知识库**：稳定业务知识、代码入口、分析模式和执行约束；
- **应用闭环**：执行、评测、诊断、知识生产。

其重要变化是放弃“整个知识库必须完美”的目标，改为：

```text
稳定方法、路由与门禁 → 高质量 Skill
业务私域知识         → 可自动生产的 KnowledgeRepository
知识是否保留         → 下一轮同输入重放与独立评测
```

为了降低错误知识污染：

- 评测 GT 由 PRD、最终技术方案、MR 和真实代码交叉形成证据锚点；
- 诊断不直接继承评测结论，而是重新从原始证据和 Trace 定位最早偏离点；
- 诊断产出的 `prescription.md` 只是低信任调查线索；
- 知识生产需要重新检索文档和代码、查重、路由、质量门禁和 Git 审核；
- 指标未改善或出现退化时，不应合入候选知识。

当前尚缺一套稳定评价“知识工程自身是否变好”的指标，这也是该方案明确承认的限制。

### 数据 Agent：端到端不等于一步生成

数据 Agent 分享把写 SQL、找数据、搭看板、分析、洞察和报告串成全流程，但强调数据理解、分析执行和结果校验应拆成可控步骤。这与 Aide 和知识工程的共同点是：领域 Agent 不是一个万能提示词，而是一组有明确输入输出和验证门禁的阶段。

## 四、个人 AI Coding 方法与工具选择

AI Coding 经验分享从个人工作法补充了生产约束：

- 模型选择需要在速度、额度和智能度之间动态平衡；
- Agent 工具的差异不仅是模型，还包括 Harness、会话管理、工具和插件生态；
- 复杂任务应事前确认理解和范围、过程中披露关键动作、完成后汇总文件与遗留问题；
- 生产环境要遵守所有权边界和最小化改动，不把相邻问题顺手修掉；
- 重型 SDD 并非默认最优：简单任务可能直接修改后人工 Review，复杂任务也要防止前期 Spec 过重、最终 Diff 无人能审。

这组经验与其他三个主题簇形成互补：平台提供工具和治理能力，个人仍要通过模型分层、任务分级和最小改动控制风险。

## 跨簇共同结论

### 1. 模型能力正在解耦

生成、决策、界面理解、检索、精确计算不再默认由同一个模型承担。系统应把每个步骤分配给“满足要求的最低成本能力”，并保留升级路径。

### 2. Harness 是生产系统的控制面

生产级 Agent 的关键能力集中在 Harness：状态、上下文、工具、权限、审批、重试、故障恢复、版本、追踪和评测。更强的模型不能替代这些能力。

### 3. Context 必须被组织而不是无限堆积

四类实践都强调选择性上下文：

- Jev 只接收判断所需的最小状态；
- Agent Team 只共享协作所需的信息；
- Aide 按域和阶段渐进披露知识；
- 知识工程区分事实资产、长期知识和诊断线索。

### 4. 评测决定系统能否持续进化

没有稳定输入、指标、证据和对照回放，自我改进容易退化为“模型改了自己并宣布更好”。候选改动必须在独立评测中证明收益，并检查旧能力保留和业务副作用。

### 5. 人工入口应由风险和不确定性触发

人工不应逐步盯住所有执行，而应集中在：

- 低置信度和候选空间缺失；
- 高风险工具调用与外部写入；
- 规则冲突和业务边界未定义；
- Gate 验收、版本晋级和知识合入；
- 系统无法恢复或证据不足。

## 建议的统一架构

```text
环境与组织事件
      ↓
状态/世界模型/任务资产
      ↓
Router：选择路径、模型与 Skill
      ↓
┌─────────────┬──────────────┬──────────────┐
│ 决策模型     │ 生成式模型    │ 确定性代码    │
│ 路由/评分    │ 规划/生成      │ 计算/执行      │
└─────────────┴──────────────┴──────────────┘
      ↓
Task / Session / Tool / Handoff
      ↓
Gate：测试、评测、权限、人工审批
      ↓
结果、Trace、反馈与业务指标
      ↓
诊断 → 知识/Skill/Harness 候选更新
      ↓
固定输入重放与版本晋级
```
