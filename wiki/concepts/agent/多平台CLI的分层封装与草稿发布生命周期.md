# 多平台 CLI 的分层封装与草稿发布生命周期

## 适用范围与证据边界

本文整理多平台命令行工具的工程设计原则，供 Agent 工具建设参考。内容来自一次内部客户端实现调研后的泛化分析，省略内部平台标识、接口地址、源码位置和精确配置。本文不是任何具体产品的接口文档，也不把客户端代码的行为当作服务端成功执行的证据。

关联：[[Agent任务分流：工作流与智能体边界]]、[[Agent框架选型与工程维度]]。

实施时可使用 [[CLI开发检查清单]]，按接口确认、命令契约、分层开发、专项测试、集成验收和发版顺序执行。

## 按用户任务组织命令

命令行工具可以复用平台已有接口，把网页上的操作转成可组合的命令。调度、版本管理和发布状态仍由平台维护；客户端负责参数、认证、请求编排和结果解释。

网页的一次操作可能调用多个接口，因此命令和接口不必一一对应：

- 单一资源、语义清楚的接口，可以直接对应一条命令。
- 完成同一任务需要多个接口时，在业务服务层编排。
- 一个接口通过模式参数承载多个动作时，可以拆成不同命令，分别说明副作用。

## 分层与共享基础设施

| 层 | 职责 |
|---|---|
| 命令注册 | 命令名、参数、帮助说明与输入文件读取 |
| 处理入口 | 输入校验、调用业务服务、组织输出 |
| 业务服务 | 多接口编排、资源标识解析、字段合并、去重与回读 |
| 接口客户端 | HTTP 调用、响应解析、类型转换与错误归一 |
| 共享基础设施 | 区域路由、认证、凭据存储、日志、配置与输出 |

区域差异可能涉及网关、请求字段和认证方式。把这些差异集中到配置和认证适配中，可以减少业务命令里重复的条件分支。不能假定所有平台都使用同一种 JWT，也不能假定控制台接口都是稳定的公开接口。

文本输出服务人阅读，结构化输出服务脚本和 Agent。帮助文档、技能说明与 MCP 等入口应围绕同一组业务能力维护，避免不同入口形成不同的操作语义。

## 代码草稿与调度草稿

编辑节点和调度任务可能是不同资源，有各自的标识与配置存储：

- 编辑草稿承载代码或 Notebook 内容，以及运行元数据。
- 调度草稿承载上游依赖、周期、队列、重试等配置。
- 两种资源通过关系查询关联；不能把其中一个标识直接当作另一个使用。

保存代码不等于提交版本，提交版本也不等于发布生效。部分平台允许同一次提交请求选择“只提交”或“提交后发布”，客户端应把这个选择写入明确的参数和输出。

## 修改依赖的保护与边界

当平台保存接口要求完整草稿时，增量修改需要客户端先读取原稿，再合并新增依赖。建议流程为：

1. 读取草稿，解析依赖和配置。
2. 按上游任务、周期偏移和偏移类型识别重复依赖，生成预览。
3. 写入前再次读取；若草稿已变更，停止本次写入。
4. 保存合并后的草稿，保留无关字段。
5. 回读并核验原依赖、新依赖和无关配置。

客户端的读前检查无法消除最后一次读取与写入之间的竞态。要保证原子条件更新，需要服务端提供版本号、条件写入或比较并交换机制。写后校验只能发现结果不符合预期，不能证明写入期间没有覆盖他人的修改。

若请求已经写入，但回读校验失败，应报告“已写入、核验失败”，避免盲目重试。

## 提交与发布的结果契约

操作结果至少需要区分请求已接收、等待检查、等待审批、提交完成、发布完成和发布失败。一个顶层成功字段不足以表达这些状态。

客户端需要检查接口返回的阻塞标记、事件标识和版本信息，必要时查询后续状态。流水线默认值、审批要求和自动发布开关也属于命令契约，不能只依靠动词名称判断副作用。

## 新能力建设与验证

接入新能力时，先确认平台文档或控制台请求的实际契约，再确认资源标识、认证、区域差异及草稿生命周期。随后按分层实现，并同步命令帮助和 Agent 使用说明。

离线测试适合验证参数解析、响应重塑、编排顺序和错误传播；受控环境中的集成验证用于确认真实接口行为。源码、帮助和技能说明可以相互核对，但若来自同一个项目，就不构成独立的服务端验证。

对 Agent 而言，确定的写入流程适合由 CLI 的业务服务层执行。Agent 负责选择任务和解释结果，固定流程中的去重、合并、回读与状态判断应由可测试的代码承担。见 [[Agent任务分流：工作流与智能体边界]]。
