# 自回归掩码、解码与生成评测

## 三个容易混淆但分属不同层次的概念

| 层次 | 概念 | 它回答的问题 |
|---|---|---|
| 模型结构 | 因果掩码（causal mask） | 当前 token 可以看见哪些上下文？ |
| 推理策略 | 贪婪解码（greedy decoding） | 下一 token 从候选中怎样选？ |
| 评测口径 | pass@1 | 一次端到端尝试是否成功？ |

将三者分开，才能避免把模型结构、运行时策略与实验得分混成“模型本身更强”。本页的解释性原始材料为 [[../../../raw/transcripts/大模型基础概念：因果掩码、pass@1与贪婪解码|大模型基础概念转录]]。

## 因果掩码：禁止未来信息泄漏

自回归语言模型按 $p(x_{1:T})=\prod_t p(x_t\mid x_{<t})$ 分解序列概率。因果掩码让位置 $t$ 的注意力不能访问未来位置，保证训练时不会借用生成时本不具备的信息。它是 token 顺序上的信息约束，不是因果推断的“干预—因果效应”概念。

- 对解码器式 LLM：通常是自注意力层的基础约束。
- 对双向编码器：通常不使用同样的未来遮挡；它可同时利用左右文。
- 对编码器—解码器：通常由解码器自注意力采用因果掩码，编码器可双向编码输入。

[[来源-LATS-统一推理行动规划-ICML2024]] 的搜索式推理是在此类逐 token 生成能力之上额外增加候选扩展、环境反馈与选择；搜索不改变“禁止偷看未来输出”的自回归约束。

## 用作用户嵌入器时：掩码是适配选择

当 decoder-only LLM 被用于编码完整用户历史时，causal、hybrid 与 bidirectional mask 比较的是**表征训练的可见上下文与过渡路径**，不是贪婪/采样等解码策略，也不是脱离任务的能力排名。[[来源-DecoderOnly用户表征注意力掩码-2026]] 以 GG-SM 先按梯度引导软开放未来 token、再平滑转向双向注意力；这支持其特定离线用户表示任务中的稳定性与质量结论，但不自动替代需要增量追加、低延迟服务的因果架构。相关的场景条件化接口见 [[LLM用户表征基础模型与场景适配]]。

## 贪婪解码：低成本的局部选择

贪婪解码在每一步取条件概率最大的 token。它具备确定、便宜、无需维护候选集的优点，但每一步局部最优不保证整个输出最优，也较少探索替代轨迹。

- 在短答案或确定性要求较高的场景，它常是合理的延迟/成本基线。
- 在开放式长生成、需要多步推理或易重复的任务，早期选错可能被后续放大；采样、beam search 或“生成多个候选后用验证器/搜索选择”可换取探索，但成本和结果协议随之改变。
- [[来源-Qwen2.5与Qwen3微调深度调研-2026-06-21]] 中“Thinking 模式避免贪婪解码”是该转录给出的特定工程建议，不能概括为所有模型、所有任务都不应使用贪婪解码。

## pass@1：单次尝试的成功率

pass@1 在每个题目上只计一次独立候选是否通过任务判定（如代码测试），再取题目平均成功率。它更接近“不重试便交付”的端到端体验。

- pass@k 允许从 $k$ 个候选中存在一个通过；候选数、温度、去重、测试器与工具预算会系统性影响该数字。
- 使用 MCTS、反思、工具调用或多候选重排的系统，即使最终只输出一个答案，也不等同于“无搜索单次前向生成”的 pass@1。
- 因而引用 [[来源-LATS-统一推理行动规划-ICML2024]] 或 [[来源-Kimi-Agent-自主持续优化研究报告]] 的 pass@1 时，必须同时记录 benchmark、候选/搜索预算、解码设定、判定器与模型版本；不同报告的数字不宜横向汇总成统一能力排名。

## 设计与报告检查表

1. **结构**：是否明确模型是自回归、双向还是编码器—解码器？掩码作用在哪个注意力模块？
2. **生成**：是否报告贪婪、采样、beam 或搜索/重排？温度、top-p、最大 token 与随机种子为何？
3. **评测**：pass@1 的“一次”是一次模型调用，还是一个允许搜索、工具、重试的系统回合？
4. **比较**：若其中任一项不同，应描述为不同系统协议下的结果，而非纯模型能力的直接排序。
