# Agent框架选型与工程维度

> 基于 `raw/search/` 在 2026-06-20 的归档批次抽取，强调“可交付工程”而非仅模型调用。

## 问题定义

在 Agent 框架语境下，选型不再是“哪个 API 更方便”，而是“如何把 LLM 能力落到可控、可观测、可维护的业务流程”。

## 关键维度

### 1) 代理能力 vs 工作流能力

- 代理能力关注：任务理解、工具调用、对话/计划。
- 工作流能力关注：显式步骤编排、状态检查点、人工介入、恢复与重试。
- 实务上两者应分层，而不是混为“一个大黑盒 Agent”。

### 2) 结构化契约与系统落库

- 是否支持 schema 化输出、字段校验、重试策略。
- 是否能直接对接工单/CRM/审计等下游系统。

### 3) 受控执行边界

- 工具调用是否可审计、可鉴权、可限流。
- 是否支持 MCP / 函数调用 / 沙箱执行等安全边界。

### 4) 可观测与运维

- 是否具备 trace、指标、错误定位与评测能力。
- 是否支持上线后的持续迭代闭环（而非仅开发期 demo）。

### 5) 生态与语言栈匹配

- Python 生态：组件丰富、社区体量大、迭代快。
- Java 生态：与既有企业系统整合、性能与治理诉求常更强。

## 可复用结论

1. **先分层再选框架**：先定“需要 Agent 还是 Workflow，或二者组合”，再选具体工具。
2. **工程约束优先于榜单热度**：星标数是流行度，不等于组织适配度。
3. **把“可观测 + 可回滚”当成上线门槛**：没有运维闭环的 Agent 系统难以规模化。

## 补充织入（2026-06-23）

- 新增来源 [[来源-LLM智能体规划综述-USTC-Huawei-2026-06-23]]：该综述提出的五大规划方向中，”任务分解”对应 workflow 编排能力，”反思与改进”对应自纠错闭环——这两项是选型时需要评估的核心规划维度。SwiftSage 的”快慢思考”双系统设计也是分层架构的典型案例。

- 新增来源 [[来源-工具学习与基础模型综述-Tsinghua-2026-06-23]]：该综述提供了工具学习的四组件框架（控制器-工具集合-环境-感知器），直接支撑本页”代理能力 vs 工作流能力”的分层判断。其中工具理解（零样本/少样本提示）、内省式 vs 外向式推理的区分，以及工具调用审计需求，为”受控执行边界”和”结构化契约与系统落库”两个维度提供了学术理论支撑。
